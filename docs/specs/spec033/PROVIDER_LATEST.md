# BMRK / BRA on-demand FRED date check

Both pages offer **Check FRED latest** for SOFR and DGS10. The user explicitly starts the check; loading either page does not contact FRED. A server-only `FRED_API_KEY` is optional. Without it, both series show that the check is not configured and no provider request is made. The warehouse remains the source of qualified observations and analytics.

The separate `/api/benchmark-provider-latest` endpoint calls FRED's [series observations API](https://fred.stlouisfed.org/docs/api/fred/series_observations.html) over HTTPS, with the series fixed to the two supported identifiers. It requests the 100 most recent returned records in descending observation-date order, with a single New York calendar as-of date fixed when the check starts. Missing-value markers are excluded; finite zero and negative values remain valid. Future-dated observations are counted and excluded. If the latest 100 records contain no usable as-of observation, the check says so; it does not claim that older history is absent. Invalid or incomplete payloads, errors, timeouts, and rejected responses do not produce a date.

The UI displays each successful observation date and the actual check completion time, then compares the date separately with qualified Gold and the latest verified warehouse source. A same-date result does not establish that values or revisions match. The date is not a publication timestamp, and a FRED response is not inserted into the warehouse, qualified-history array, analytics, or exports. The snapshot PDF explicitly states that it does not include this independent check.

The endpoint returns dates and statuses only, uses `Cache-Control: no-store`, does not return or log the API key, disallows redirects, limits each response to 128 KiB, and times out after eight seconds. A shared PostgreSQL gate allows one check (two FRED requests) per 30 seconds across application instances using the same database. It limits only this endpoint, not other users of the FRED key. If the gate cannot be reached, the check is paused and no FRED request is made. A failed retry clears the prior check from the UI. Partial provider failure is reported per series; it does not discard independently qualified warehouse history. Provider rate limits, access locks, and recognized key rejections are reported separately without exposing FRED error text. See [FRED error codes](https://fred.stlouisfed.org/docs/api/fred/errors.html).

## Provisioning the shared limiter

Provision a **separate application-control PostgreSQL database**, never the EcoMedallion warehouse. Apply [PROVIDER_LIMITER_POSTGRES.sql](PROVIDER_LIMITER_POSTGRES.sql) once using a provisioning role. Grant the runtime role schema USAGE and table SELECT, INSERT and UPDATE; runtime requests do not create tables. Set the server-only `BENCHMARK_PROVIDER_LIMIT_DB_URL` to this database on every application instance, and set the server-only `FRED_API_KEY`. Connection and query timeouts are 2.5 seconds. If the URL, table, permissions, or database is unavailable, the endpoint fails closed. Do not use a transaction-pooling configuration that changes the atomic PostgreSQL statement semantics. The gate uses an atomic [INSERT with conflict update](https://www.postgresql.org/docs/current/sql-insert.html) and the database clock. No rate values or provider responses are stored there.

### Local development setup

With Docker running and the `postgres:16` image already available, run `npm run setup:benchmark-control` once. The script creates a dedicated, loopback-only PostgreSQL container named `market-terminal-benchmark-control`, a persistent named volume, and a restricted application role. It provisions the schema, verifies the role permissions and writes its generated application URL to the ignored `.env.local` with owner-only permissions. It refuses to overwrite an existing setting or reuse an existing container or volume. The script does not touch EcoMedallion. It does not configure the FRED key; keep that separately in a server-only environment file.

The container uses Docker's `unless-stopped` restart policy. After Docker is started, restart the application to load `.env.local`. If the container was manually stopped, start it with `docker start market-terminal-benchmark-control`. Data in the named volume survives container restarts. For multi-instance checks, all instances must use the same control database; this local Docker setup is for development and does not provision a deployed database.

## Validation and limits

Tests cover missing configuration, shared limiter failure and contention, provider rate limits and access locks, recognizable credential errors, partial failures, future and missing observations, malformed/incomplete/oversized payloads, timeouts, credentials not appearing in responses, and client-side validation. Browser tests exercise both pages, separate date comparisons, and failure and recovery. The warehouse-only Tier A policy remains in force; this informational check never supplies Tier A data.

On 2026-11-12 at 17:34 UTC, an isolated end-to-end check used a configured server-side FRED key and a disposable PostgreSQL limiter. Both live responses passed the provider contract: the latest usable as-of observation dates were **2026-11-10 for SOFR** and **2026-11-09 for DGS10**. The provider checks completed at 17:34:55 UTC, with a 2026-11-12 New York as-of cutoff. An immediate retry was rate-limited. These are observation dates, not publication timestamps, and can change with later checks. The live response supplied dates only and did not enter qualified history or analytics.

A separate read-only local warehouse check found qualified Gold and verified warehouse source dates of 2026-11-09 for both series. Thus, at this check, the provider SOFR observation was one calendar day later than the retained warehouse observation; the DGS10 dates matched. A matching date does not prove the values or revisions match. No warehouse writes were made. Browser and unit tests use fictional fixtures and are not production data.

On 2026-11-12, the local persistent limiter was provisioned separately from EcoMedallion. A live browser check on BMRK displayed both series; a BRA instance sharing the limiter was rate-limited. The limit persisted across a control-database restart and an application restart, and BRA returned live dates after the cooldown. This check ran without connecting the application to the warehouse; its purpose was provider and limiter verification.

The initial live test used a temporary limiter. Normal application instances must be configured with both server settings above before the provider-date check can run. Never paste the key into a client or log.
