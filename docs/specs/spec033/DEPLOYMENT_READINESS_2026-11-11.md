## Controlled refresh plan

1. **Identify and coordinate the actual writer.** Determine its owner, scheduler, backend, target database and deployed commit; resolve the old `running` records with the owner and prevent concurrent writes for the change window. Do not infer inactivity from this snapshot. Confirm that the writer includes the merged upstream as-of guard and schema migration. EcoMedallion PRs [#98](https://github.com/thatquantguy44/EcoMedallion/pull/98) and [#100](https://github.com/thatquantguy44/EcoMedallion/pull/100) are merged, but that does not establish deployment.
2. **Establish recovery and scope.** Inventory all Gold objects and consumers affected by the selected writer, capture a consistent backup of the affected warehouse and its Bronze/Silver/audit evidence, and demonstrate restoration to an isolated target. Record the backup identity, restore result and rollback owner. Keep original capture files accessible. The PostgreSQL `build_gold` path replaces shared latest-observation data and rebuilds other models; it is not a BMRK-only update. The inspected `PostgresWarehouse` constructor defaults to schema creation/migration, commits those changes, and may backfill observation history before `build_gold` begins. Back up before constructing the write-side warehouse; do not assume the later build transaction rolls back initialization. `initialize=False` avoids that startup but does not make later operations read-only or validate schema.
3. **Rehearse the exact candidate and target shape.** Freeze the intended upstream commit, configuration and New York cutoff; use a complete, consistent copy of the intended inputs in isolated PostgreSQL. Check schema migration, future observation and revision exclusion, all 16 board rows and dependencies, dates, values, spreads, statistics and provenance fields. Reconcile the other affected Gold outputs and their consumers. Fail on missing evidence, unexpected differences or inadequate coverage; do not substitute simulated data. The previous 16-series test alone does not establish whole-warehouse parity.
4. **Prepare the operator procedure.** Identify the tested entry point and explicit destination, capture the pre-change database and cutoff, define acceptance thresholds and monitoring, and have the owner approve the exact execution and rollback steps. The inspected `gold` CLI selects SQLite with `--local` and Spark otherwise; it should not be assumed to rebuild this PostgreSQL database. The SQLite-to-Postgres publisher has separate replacement and evidence limitations documented in [historical analysis](HISTORICAL_ANALYSIS.md).
5. **Only after approval, perform and verify the controlled change.** Pause or coordinate writers, run the specifically tested PostgreSQL path and schema migration, then reconcile the actual board and downstream objects against the same-cutoff evidence-backed reference. Check both BMRK and BRA, missing-data behavior and recent run health. If checks fail, follow the tested recovery procedure and preserve the failure evidence. Re-run all checks at execution time; this dated snapshot is not an authorization or a current-state guarantee.

Provider publication timestamps and the actual latest FRED values remain unknown until independently checked. A warehouse refresh cannot establish them by itself.
