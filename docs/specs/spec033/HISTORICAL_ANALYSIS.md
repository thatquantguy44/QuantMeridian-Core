# BMRK / BRA historical analysis and Gold freshness

## Delivered

Both pages share a historical explorer backed by the qualified benchmark API. The initial snapshot is up to 520 observations per series. The explorer requests up to 1,000 older observations at a time for one series, with an exclusive `before` date; the server enforces an absolute limit of 2,000 rows and returns the page boundary separately from the latest retained Gold date. Each page independently reconciles observations against their source evidence. A failed or unverified older page is not merged; independently qualified current history remains visible. The explorer can continue until the earliest retained date, subject to available evidence and service query limits.

The 1-, 2-, and 5-year windows use calendar months and the all-loaded window uses all fetched observations. Charts, statistics, comparisons and CSV export use the same selected window. Calendar comparisons select the latest observation on or before the target, disclose that date, and require lag within both the frequency threshold (daily 5, weekly 10, monthly 45, quarterly 110, annual 400 calendar days) and horizon cap (1D: 3 days; 1W: 7; 1M: 31; 3M: 93; YTD and 1Y: 400). The current observation is never reused as the prior value. Percent-denominated rate differences are shown in basis points. Insufficient coverage is unavailable.

The explorer shows level range, mean, percentile (at least 10 observations), sample z-score and the sample standard deviation of consecutive observed level changes. The rolling chart uses 20 consecutive observed changes; a window spanning a cadence-sized gap is unavailable. Volatility is not annualized, and observation intervals may differ. Lines break at oversized gaps, and chart horizontal spacing follows observation order, not elapsed calendar time. If more than 20,000 observations are loaded, the level chart shows only the most recent 20,000; tables and CSV use the full selected sample. CSV includes per-page check timestamps and the combined evidence methods for the loaded sample. Pages may have been retrieved at different times; this is latest-revised history, not a consistent point-in-time snapshot.

Spread calculations use exactly matched dates and disclose their sample coverage. Correlations use common dates across the available group, up to 60 matched level changes, and require at least five changes and nonzero variance; no missing values are filled. The BMRK spread panel can also load older pages for both legs in batches of up to 1,000 observations per leg. It adds a batch only if all requested pages pass qualification, and cancels an in-flight request when the pair or snapshot changes. The chart, statistics, and spread CSV use the same selected window; the display shows matched and unmatched counts and each leg's loaded and retained coverage. The CSV includes both observed inputs, units, source links, page evidence methods and page check/as-of times. The comparison board and correlations use the initial loaded snapshot; the spread panel's older pages do not modify current cards. The chart caps rendering at the latest 20,000 matched observations while the selected-window statistics and CSV use the full sample. The snapshot PDF uses those same initial histories, includes dated calendar and rolling statistics, and retains the source table; its scope is explicit. The explorer's CSV exports the visible history, including older pages.

## Spread history verification

On 2026-11-12, a read-only local PostgreSQL check requested ten current qualified observations and one older page per leg for DGS10 and DGS2. Both older pages contained 1,000 qualified observations; the combined samples had 1,010 exact matched dates from 2022-10-25 through 2026-11-09. PostgreSQL sessions were forced read-only. This verifies the retained warehouse and qualification path at that time, not current FRED publication or a point-in-time archive. Browser tests separately cover the panel, rejected pages, retry, pair changes and CSV window consistency using clearly fictional fixtures.

## Read-only freshness investigation

On 2026-11-10 America/New_York (2026-11-11 UTC), the local PostgreSQL warehouse had SOFR and DGS10 Gold observations through 2026-10-29, while separately qualified Silver source observations reached 2026-11-09. The latest Gold ingestion timestamps for those series were 2026-10-31 UTC; Silver ingestion timestamps reached 2026-11-11 UTC. These are retained warehouse timestamps, not a check of the provider's current publication. The last source inventory recorded 23 series with a newer verified warehouse source record.

The latest IORB Silver observation in the read-only inspection was dated 2026-11-12, later than the inspection date. It failed source qualification; the separately qualified earlier Gold history remains visible. Its cause has not been established. The audit table also showed multiple recent runs with different outcomes and one recorded as running; these records alone do not prove which event caused the Gold lag or whether a process was still active.

The upstream PostgreSQL Gold builder materializes `gold.fred_latest_observation` from Silver inside a transaction by deleting and reinserting the shared table, then builds downstream products including `gold.benchmark_rate_board`. This is broader than BMRK/BRA. The upstream `gold` CLI in the inspected version selects SQLite when `--local` is supplied and otherwise Spark, so do not assume that command targets the PostgreSQL database. The terminal's `publish_fred_gold_to_postgres.py` is a separate SQLite-to-Postgres publisher: by default it copies Gold, audit and meta, and its optional serving-only mode starts at 2020. It does not by default publish the Silver and Bronze evidence required by the qualification boundary. Its target replacement also drops objects; it is not a safe one-series refresh.

Before a production refresh, identify the actual writer/backend and active runs, inspect the future-dated IORB record and source captures, take the appropriate backup, run a controlled rebuild/publish through the correct pipeline, and reconcile Gold dates, values, board dates and evidence against Silver. Confirm cross-module effects and evidence availability before promoting the result. No warehouse records were changed by this investigation.

The subsequent [Gold refresh rehearsal](GOLD_REFRESH_REHEARSAL.md) records the later warehouse state, IORB evidence, and corrected New York as-of handling.

## Remaining work

The current rule-based regime is a visible baseline, not a trained classifier. No independent, documented regime-label set or chronological holdout has been qualified here, so a model trained on the existing rules would mainly reproduce those rules rather than demonstrate incremental value. Defer ML activation until labels, chronological evaluation, class balance and a baseline comparison are available. Provider-latest checks, a controlled Gold refresh, historical correlation paging, and production-backend integration beyond local PostgreSQL also remain open.
